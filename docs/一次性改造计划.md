# FengHuoChess 一次性改造计划

## 1. 改造目标

- 把当前“脚本集合”改造成可维护的 Python 项目结构（`src` 布局）。
- 拆分 `game.py` 的混合职责（规则、状态、渲染、输入耦合）为清晰模块。
- 形成稳定的“核心规则层 + UI 展示层”边界，方便后续加 AI、联机或重放。
- 补齐基础工程能力：可安装、可测试、可运行、可扩展。

## 2. 现状问题（基于当前代码）

- `game.py` 过大，混合了：
  - 游戏状态管理
  - 胜负判定
  - 阶段推进
  - 出锋/截锋处理
  - Pygame 绘制
  - 按钮和界面文案逻辑
- 规则层依赖 Pygame，不利于单元测试。
- `main.py` 事件处理和游戏流程耦合，无法复用。
- 配置、文案、规则常量集中在 `config.py`，缺乏分层。
- 缺少统一入口（包入口 / CLI）、测试目录、工程元数据。
- 悔棋模块存在系统性缺陷：
  - 栈语义不一致：`save_state()` 在落子前入栈，`undo()` 采用“弹栈后恢复栈顶”，导致回滚步数错误。
  - 已复现：连续走 3 手后执行 1 次悔棋，棋子数从 `3` 变为 `1`（预期 `2`）。
  - 快照字段不完整，未覆盖 `last_exposure_player`、`consecutive_exposure`、`exposure_occurred`、`checked_positions`、按钮状态等运行态字段，易产生“回档后状态残留”。
  - 缺少悔棋行为测试，回归时无法及时发现栈错乱问题。

## 4. 旧文件 -> 新模块映射

- `main.py`
  - -> `src/fenghuo_chess/ui/pygame_main.py`
  - -> `src/fenghuo_chess/app.py`（入口装配）
- `game.py`
  - `reset_game/save_state/undo` -> `domain/models.py` + `services/history_service.py`
  - `is_valid_move/check_win/check_stage_transition` -> `domain/rules.py`
  - `determine_winner/count_threes` -> `domain/scoring.py`
  - `draw/highlight_area` -> `ui/renderer.py` + `ui/panels.py`
  - `make_move` 主流程 -> `application/game_controller.py`
- `exposure.py`
  - -> `services/exposure_service.py`
- `broadcast.py`
  - -> `ui/broadcast.py`
- `config.py`
  - 视觉常量 -> `constants/colors.py` / `constants/ui.py`
  - 规则常量 -> `constants/gameplay.py`
  - 介绍文案 -> `docs/玩法规则.md` + `ui/panels.py` 中最小展示文案

## 5. 函数重分配原则

- 规则函数必须“无 Pygame 依赖、可纯函数测试”。
- `GameController` 只协调流程，不直接画图。
- Renderer 只读状态，不改状态。
- 输入映射只做“坐标/点击 -> 意图命令”，不直接改棋盘。
- 文案与播报触发分离：
  - 规则层返回事件（如 `WIN`, `EXPOSURE_TRIGGERED`）
  - UI 决定如何显示。

## 6. 一次性迁移步骤（建议 8 个提交）

## Step 0: 悔棋模块纠偏（前置，必须先做）

- 建立 `HistoryService` 的统一模型：
  - 使用 `snapshots + cursor`（指针）语义，禁止“逻辑层直接 pop + 隐式恢复”。
  - 明确“1 次悔棋 = 回退 1 个完整回合（玩家落子 + 自动截锋连锁 + 阶段切换）”。
- 调整快照时机：
  - 在一次完整动作结算结束后再提交快照（post-commit snapshot）。
  - 初始化时只保留 1 个初始快照，禁止重复压入同态快照。
- 定义完整快照字段清单（最少包含）：
  - 棋盘与回合：`board/stage/current_player/game_over/winner/stage_positions`
  - 出锋链路：`exposure_message/exposure_positions/exposure_markers/exposure_occurred/last_exposure_player/consecutive_exposure/checked_positions`
  - 模式链路：`game_mode/mode_locked`
  - UI 交互态：`restart_button_state/restart_button_press_time`
- 统一悔棋入口：
  - 仅允许 `GameController.undo()` 修改历史，UI 不直接改 `history`。
  - 悔棋失败（栈底）需返回明确状态，不做隐式副作用。
- 新增悔棋专项测试（必须通过）：
  - 1 手、2 手、3 手分别悔棋，严格验证只回退 1 手。
  - 含截锋连锁的回合悔棋，验证整回合原子回退。
  - 跨阶段临界点悔棋，验证 `stage/mode_locked/stage_positions` 一致恢复。
  - 胜负产生回合悔棋，验证 `game_over/winner/current_player` 恢复正确。

## Step 1: 工程脚手架

- 新增 `pyproject.toml`，定义包名、依赖、运行入口。
- 建立 `src/fenghuo_chess` 包结构和 `tests/` 目录。
- 保持旧入口可运行（过渡期双入口）。

## Step 2: 抽离领域模型

- 建立 `Player/Stage/GameMode` 枚举。
- 建立 `GameState` dataclass（棋盘、阶段、当前玩家、模式、历史标记）。
- 把硬编码状态字段集中到 `GameState`。

## Step 3: 抽离规则引擎

- 从 `game.py` 提取：
  - `is_valid_move`
  - `check_win`
  - `check_stage_transition`
  - `determine_winner/count_threes`
- 对上述逻辑补单元测试，确保行为等价。

## Step 4: 抽离出锋服务

- 把 `ExposureDetection` 改为 `ExposureService`。
- 输入输出改为显式参数（state + last_move -> effects）。
- 加入连锁出锋测试（含双端出锋、阶段 3 双截锋）。

## Step 5: 引入应用层控制器

- 实现 `GameController`：
  - `make_move`
  - `undo`
  - `reset`
  - `change_mode`
- 控制器串联“规则 -> 出锋 -> 阶段 -> 事件”。

## Step 6: 重写 UI 组织

- `pygame_main.py` 只保留事件循环与窗口生命周期。
- `renderer.py` 专注绘制。
- `input_mapper.py` 统一处理点击区域和棋盘坐标换算。
- 迁移 `broadcast.py` 到 `ui/` 并保持动画行为。

## Step 7: 清理旧代码并收口

- 删除根目录旧脚本（`main.py/game.py/config.py/exposure.py/broadcast.py`）。
- 更新 `README.md` 运行方式与结构说明。
- 完整跑测试与手动对局回归。

## 7. 验收标准（DoD）

- 能通过 `python -m fenghuo_chess.app` 启动游戏。
- `domain/` 与 `services/` 不依赖 Pygame。
- 单测覆盖关键规则：
  - 阶段 1~4 胜利判断
  - 阶段推进
  - 出锋/截锋连锁
  - 终局计分
- 单测覆盖悔棋关键场景：
  - 连续 3 手后悔棋仅回退 1 手
  - 含截锋连锁回合的原子回退
  - 跨阶段回退后的可落子区域一致性
- 悔棋、重开、模式锁定行为与现版本一致（或在文档明确差异）。

## 8. 风险与应对

- 风险：重构中行为偏移（尤其是出锋连锁和悔棋快照）。
  - 应对：先补测试再迁移，保持每步可回归。
- 风险：UI 拆分后坐标转换错误。
  - 应对：增加输入映射测试用例与可视化调试坐标。
- 风险：一次性大改冲突高。
  - 应对：按 8 步提交，任何一步都可独立回滚。

## 9. 改造后建议

- 增加 `Replay`（保存并回放走子序列）。
- 增加 `AI` 接口（先随机策略，再极小化搜索）。
- 增加“规则变体配置化”（阶段数、连子长度、出锋惩罚强度）。
